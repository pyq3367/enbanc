# 000 — Why this exists

## The observation

A run history from the tool this grew out of:

| run | cursor | last verdict | rounds | outcome claimed |
|---|---|---|---|---|
| A | P5 | revise | 7 | delivered |
| B | P5 | revise | 1 | delivered |
| C | P5 | revise | 3 | delivered |
| D | P5 | revise | 2 | delivered (both workers had failed) |
| E | P5 | revise | 6, escalated 4x | delivered |
| F | P5 | **pass** | 3 | delivered |

> Note, added later: this page records where the project came from. The rules it
> argues for have since changed shape — the verdict set is now three
> (`pass` / `conditional_pass` / `revise`), and delivery requires an explicit
> acceptance when findings remain open. Current rules: [rules.md](reference/rules.md).


Five of six had a delivery cursor that did not match the last review result.
This does not establish that they never passed an earlier review, or that every
rejection was justified. It shows that the cursor could be moved without checking
the recorded verdict.

This is the whole motivation: **a run's state was an assertion, not a fact.**

## Why a better model does not fix it

The failures are not about capability. They are about who is allowed to declare
completion:

- **Execution hallucination** — "I ran the checks." Nothing ran.
- **Artifact hallucination** — "I wrote the file." The file is 0 bytes.
- **Scope hallucination** — "All criteria covered." Two of six were attempted.

A stronger model produces these less often, not never. And when it does produce
one, the stronger model is *more* convincing about it.

The structural fix is to take the declaration away from the producer:

1. completion needs a structured claim (`ready`), not prose
2. the claim is checked against the artifact, not against itself
3. the checker is not the producer
4. when the checker runs out of useful things to say, escalate — do not accept

## The cost, stated plainly

Gates can reject valid work. This project has not established a measured false-positive
rate, and the small local run history is not a benchmark. Findings need to be checked
against the actual artifact and criteria; repeated rejection is not proof of quality.
Approximate rules, including character thresholds, need calibration and human review.

So enbanc draws a line:

| Kind of check | Authority | Why |
|---|---|---|
| command exit code | **hard** — fails the round | ground truth exists |
| verifier finding, `high` | **hard** | countable, reproducible |
| verifier finding, `low`/`medium` | recorded, does not block alone | may be taste |
| judge verdict | affects the final verdict; cannot remove verifier findings | model judgment still needs review |
| producer self-report | **not evidence** | the thing under test |

And a structural choice that follows: **enbanc does not decide what "good" means.**
It enforces that *someone other than the producer* decides, and that the decision
is written down. If your criteria are vague, the gate will not save you — it will
just make the disagreement visible, which is the most it can honestly do.

## What this is not

- Not a code review tool. Code has tests; most artifacts do not. See
  [002-verifiers.md](002-verifiers.md) for what replaces tests.
- Not an agent framework. It does not spawn, schedule or host agents. It runs a
  loop around whatever produces your artifacts.
- Not a quality oracle. It cannot tell you whether a deck is persuasive. It can
  tell you that nobody independent ever said it was.

## The name

*En banc* is a court sitting as the full bench rather than a panel of three.
Cases go there when the panel cannot settle them, and the point is that the
decision is made by a body that did not build the case.

Escalation is the same move: the first judge is a panel. When it keeps finding
new problems, that is the signal to convene a fuller bench, not to ask the panel
to try harder.
